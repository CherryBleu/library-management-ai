# 图书管理系统开发宪章

## 1. 适用范围

本宪章约束本项目的需求规格、UML 模型、架构说明、数据库设计以及后续实现。所有由 Agent 生成的内容都必须经过人工审查，审查结论记录在 `18-review-checklist.md` 和 `19-ai-usage-log.md` 中。

## 2. 需求与规格基线

1. 需求以 `00-project-brief.md`、`01-clarifying-questions.md` 和 `02-requirements.md` 为来源。
2. 每个功能需求必须具有唯一的 `FR-XXX` 编号、验收标准以及对应的业务规则或用例。
3. 每条业务规则使用唯一的 `BR-XXX` 编号；借阅证、借阅数量、借阅期限、逾期和罚款规则不得只写在界面或 Controller 说明中。
4. 规格基线建立后，任何修改都必须通过人工审查，并在 Git 中留下可追踪的提交记录。
5. 暂未确定的业务决策必须记录在“待确认问题”中，不得用未经确认的假设掩盖。

## 3. UML-as-Spec

1. UML 图使用 PlantUML 文本格式，文件必须包含 `@startuml` 和 `@enduml`。
2. 用例图、领域类图和包图必须与对应的 Markdown 规格保持一致；新增元素必须同时更新关联规格。
3. 领域类图只描述领域概念、职责、关系和核心行为，不提前加入 Controller、Repository、DTO 等技术实现类。
4. 继承、关联、聚合、组合和 `include`/`extend` 关系必须表达真实业务含义，避免为了图面完整而添加无依据的关系。

## 4. 分层架构与 MVC

1. 系统采用 Presentation/Controller、Application Service、Domain、Infrastructure/Persistence 和 Test 分层，并遵循 MVC 的职责分离。
2. Controller 负责协议适配、输入校验和响应映射；业务规则放在领域对象、领域服务或策略对象中。
3. Application Service 负责组织用例流程和事务边界；Controller 不得直接依赖 Repository。
4. Repository 接口属于领域或应用边界，Infrastructure 提供实现；依赖方向指向抽象。
5. DTO 只用于接口层与应用层之间的数据传输，不替代领域实体，也不承载业务规则。
6. 权限检查必须在应用服务入口和关键领域操作处形成可验证的约束，不能只依赖前端隐藏按钮。

## 5. 设计原则

1. 不同读者类型的借阅上限和期限使用 `BorrowPolicy` 策略表达。
2. 不同借出物类型的逾期罚款使用 `FineRule` 策略表达。
3. 读者、借阅证、馆藏副本、借阅记录和预约记录具有清晰的生命周期与状态转换。
4. 借书、还书、预约和罚款计算等核心用例必须具有正常、异常和权限失败路径。
5. 事务边界必须覆盖借阅记录、馆藏副本状态和读者当前借阅数量的一致性更新。

## 6. 测试与审查

1. 每个核心用例至少覆盖一个正常路径和一个业务规则失败路径。
2. 测试计划必须覆盖借阅证无效、超出数量、存在逾期未还、馆藏不可借、归还非本馆藏书、预约排队和权限不足等场景。
3. PlantUML 文件应进行语法渲染检查；Markdown 规格应进行编号、交叉引用和人工一致性检查。
4. 测试失败时先解释原因，再进行最小修改；不得通过删除断言或降低验收标准规避失败。

## 7. Agent 使用规范

1. Agent 必须先读取相关规格，再输出计划并修改文件。
2. 一次任务只修改任务允许的文件；任务拆分应足够小，便于人工复核。
3. Agent 输出不得直接视为最终结论；人工审查人必须检查需求覆盖、业务规则、权限、数据约束、UML 关系和可测试性。
4. 每次 Agent 使用都按提示词手册第 20 条记录在 `19-ai-usage-log.md` 中。
